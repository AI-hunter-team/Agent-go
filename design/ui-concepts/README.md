# 地铁竞技：三版界面视觉方案与底层实现

日期：2026-10-30。这是视觉探索与候选技术说明，不修改 PROJECT.md 中“尚未最终选型”的状态。图片使用内置 imagegen 分别生成，属于概念效果图，尚未实现或测量浏览器运行性能。“下一班”是临时标题，四人参赛及画面数字仅为构图示例。

## 共同界面结构与检查结果

三版均表现比赛观战页：主要空间用于三维场景，顶部显示比赛状态和列车广播，侧栏显示排名与所选角色体力，场内出现简短决策说明，底部呈现事件进程。没有主动向玩家展示飞行、攻击等创造力菜单，也没有玩家比赛中直接操纵角色的按钮。

生成图整体达到了从简单造型、卡通角色到近景电影感的递进。不过图片不是可以照抄的完整交互规范：图中的领先秒数和进度条还未有正式算法依据，不能在实现时编造预测；B、C 的时间线出现了晚于当前时刻的事件，真实实时观赛页必须只显示已经发生的记录。可拖动的完整回放在赛后开放。部分导视文字和楼梯、站台关系需要重新建模校准。广播“进站倒计时”与画面已有列车的关系也需要在实际场景中明确，不能让图像替代世界规则。

## A：口袋地铁——轻量积木式 3D

![A](01-pocket-metro.png)

高位俯视和简单人物造型，整体像桌面建筑模型。奶油白、橙色和少量蓝绿强调色，配合圆角面板，轻松且易于辨认路线。趣味来自拥挤的队列、人物姿态和不同路线的选择。相对另两版，重点是规则布局与可读性。

实现建议使用 React + TypeScript + Vite 组织网页，Three.js 显示三维场景，可选 React Three Fiber 管理场景组件。以正交或弱透视相机、基础几何体、共享材质、少量灯光、预制接触阴影构成主要观感。角色可以用简单肢体和程序动画表达走、跑、等待、倒地。生成图里的细腻光照应在真实首版中简化，不必追求逐像素复现。

重复闸机、座椅和背景物件共享几何与材质。路线先用手工路点图；队列和闸机通行是独立游戏规则。碰撞用简单盒体和胶囊体，涉及跳跃、击倒时可统一使用 Rapier，而不是拿装饰模型直接做复杂碰撞。

这版三维资产和设备负担相对最低，适合先验证指导是否影响策略。画面简化仍能承载高度、跳跃和创造性动作，不必把世界锁死为二维。尚无真实模型和性能测试，不能保证具体帧率。

## B：通勤喜剧——精致卡通 3D

![B](02-commuter-diorama.png)

采用斜俯视透视镜头，人物有表情、衣物、背包和更明确的跑步姿态，站厅与站台构成立体空间。界面仍克制，但更容易让玩家关注“我的角色”。人物之间的堵路、躲避和被保安追赶可以成为喜剧性的观看内容。

网页与图形栈可与 A 相同。Blender 制作模块化站厅、角色和可复用骨骼动画，导出 GLB。角色使用走、跑、站立、受击等动画片段，通过混合衔接，配饰先适配统一骨架。场景采用预烘焙静态光照、少量动态阴影、绘制纹理和受控高光，避免把每个灯具都实现为昂贵的实时灯光。

远处角色减少细节与动画更新，重复建筑物件使用实例化。物理与判罚仍由服务器统一处理，浏览器平滑显示位置。楼梯、电动扶梯、跳跃等使用明确的通行和移动模式；普通寻路不会自动理解飞行或挖掘，需要另行设计。

成本为中等，新增工作主要是美术、骨骼、动画、镜头和遮挡。建议把这版作为正式视觉方向的优先候选：角色有辨识度，空间也仍利于观赛。图中的反射较丰富，实际实现可先削弱，保留造型、色彩与动作。

## C：都市竞速——复杂空间与电影感 3D

![C](03-cinematic-station.png)

镜头接近人物，强调前景闸机、金属和玻璃材质、远处人群与扶梯，使用冷暖光和受控反射增加临场感。角色更接近现实比例，精彩瞬间有冲击力，但观看全局路线不如 A、B 直接。

技术可继续使用 Three.js，而非必须换一套引擎。建议先以 WebGL2 路径建立兼容基线，再按实际需求评估 WebGPU；新图形接口不会自动生成电影感。资产使用物理材质、多档模型细节和压缩纹理，静态光照烘焙，动态灯与反射数量受控，后期效果按设备分档。生成图不代表浏览器已经实现实时全局光照或光线追踪。

密集人群需要共享资源、远近不同的动画精度、按需加载与视野裁剪。参赛者近景保留细节，背景乘客简化。服务端依旧使用简化碰撞体，不能用高面数装饰模型承担完整模拟。地形挖掘还涉及网格、碰撞和导航更新，并非提升画质就会顺带获得。

真实产品需要全局俯视与跟随视角切换、遮挡淡化，并避免像效果图一样在侧栏重复渲染一个没有必要的小场景。这版成本最高，主要风险在资产生产、动画、灯光与设备兼容，适合作为长期目标，不宜直接当作首版承诺。

## 三版共用的 Agent 与比赛底座

三种视觉可以共用同一套比赛模拟和工具协议。建议 Node.js + TypeScript 管理权威服务器，可用 Colyseus 管理房间生命周期和状态同步。它不自动提供本项目的奖杯、排队、创造力或裁判规则，这些需要我们实现。

服务器维护位置、资源、闸机、队列、列车、违规和普通乘客反应。Agent 服务得到权限过滤后的观察、玩家 300 字指导及局内记忆，选择基础交互或提交创造力请求；规则执行器验证、执行并返回结果。大模型无权直接修改位置或宣布胜利。

服务器持续模拟，客户端接收状态并平滑显示。日常决策、紧急事件和条件反应按项目文档设计，具体间隔实测确定。画面刷新速度和模型反应速度是不同问题，升级渲染不能解决模型延迟。

事件、决策和定期状态快照组成复盘记录。关系型数据库可保存账号、指导版本、奖杯与比赛结果；回放文件单独保存。数据库品牌、部署平台和是否需要额外队列暂不锁定。赛后报告供玩家查看，角色局内运行记忆按规则清空。

## 选择建议

A 适合最快验证玩法，B 更符合“养自己的角色并观看竞技”的整体目标，C 用于探索表现上限。三版的复杂度比较是设计判断，不是工期估算或实测数据。

先把模拟、Agent 工具、日志与视觉分离，可以用 A 的简单资产验证规则，同时按 B 的美术方向制作角色，之后逐步替换环境。无需为了画风升级重写公平性和裁判系统。

## 官方技术资料

[React Three Fiber](https://r3f.docs.pmnd.rs/getting-started/introduction) 是 Three.js 的 React 渲染器。[Three.js 文档](https://threejs.org/docs/) 包含相机、动画、实例化和渲染功能。[Rapier](https://rapier.rs/docs/) 提供实时物理、碰撞与传感器等机制。[Colyseus](https://docs.colyseus.io/) 提供多人房间与状态同步能力。具体组合是本项目的候选建议，并非这些工具已经替我们实现玩法。

## 几个术语可以这样理解

UI 是界面；TypeScript 是带类型检查的 JavaScript；React 组织网页组件，Vite 提供开发与打包工具，Three.js 显示网页三维场景，React Three Fiber 用 React 的方式组织这些场景。Blender 是建模与动画软件，GLB 是三维模型文件格式。

正交相机适合看清布局，透视相机表现近大远小。实例化让重复物件共享绘制资源，烘焙光照是预先算好静态明暗，骨骼动画用骨架驱动人物。物理材质用金属度和粗糙度等属性表现光照，多档细节让远处模型更简单。

Rapier 是碰撞与物理引擎，Colyseus 管理多人房间与状态同步，Node.js 运行服务器程序。服务端权威表示实际比赛由服务器判定；插值是在相邻状态之间补出平滑运动；快照保存某个时刻的比赛状态。WebGL2、WebGPU 是浏览器使用显卡的接口；后期处理是画面生成后的图像效果。
