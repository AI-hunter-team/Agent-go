# MVP 技术方案（Web 技术栈）

依据：[Demo方案1.1](Demo方案1.1.md)。本文把方案落为可实现的技术设计；凡标注“MVP 取值”的参数都是为了开发而定的初值，可在测试后调整，不代表产品规则已最终确认。

## 1. 目标与范围

在浏览器中跑通一局完整体验：**填写指导 → 指导整理 → 角色在二维地铁站中自主完成“买票 → 安检 → 过闸机” → 复盘**。

MVP 必须证明（方案 1.1 第十一章）：

1. 默认指导（零输入）能完成任务；
2. 不同指导带来可观察的行为差异；
3. 环境变化后角色能获得信息并调整；
4. 所有结果与环境状态一致（结果只由模拟器结算）。

不做：3D、多人、奖杯、Boss Agent、完整随机事件系统、跨局记忆。

## 2. 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 语言 | TypeScript（前后端共用类型） | 一份 `src/shared` 类型同时给前端、后端、测试使用 |
| 前端 | Vite + React 18 | 面板与报告用 React；地图用 Canvas 2D 绘制 |
| 模拟 | 纯 TS 模块，运行在浏览器 | 无 DOM 依赖，可在 Node/Vitest 中独立测试 |
| 后端 | Node 20+，Express | 只做模型代理与会话记忆；API Key 只存在服务端 |
| 模型 | Anthropic SDK `@anthropic-ai/sdk`，默认 `claude-opus-5-5` | 通过 `AGENT_MODEL` 环境变量可替换；服务端保留 Provider 接口，后续可接其他模型做对比 |
| 测试 | Vitest | 模拟器规则、确定性、离线 Agent 通关 |
| 运行 | `npm run dev` 同时启动 Vite(5173) 与 API(8787)，Vite 代理 `/api` | |

## 3. 总体架构

```
┌──────────────────────── 浏览器 ────────────────────────┐
│ UI (React)  ── 地图 Canvas / 指导面板 / 决策日志 / 复盘 │
│    │                                                   │
│ GameRunner ── 驱动固定步长模拟；决策时暂停世界          │
│    │                    │                              │
│ Simulation(sim/)     AgentClient(agent/)               │
│  唯一有效世界状态      ├─ RemoteAgent → /api            │
│  规则、NPC、保安、观察  └─ HeuristicAgent（离线规则）    │
└────────────────────────────┬──────────────────────────┘
                             │ HTTP JSON
┌──────────────── Node 服务 (server/) ───────────────────┐
│ /api/guidance/normalize  指导整理（赛前一次）           │
│ /api/agent/decide        单次决策（≤1024 token）        │
│ /api/creative/classify   创造性意图归类（封闭清单）     │
│ /api/session/:id DELETE  局后清空局内记忆               │
│ SessionStore（内存）：system 提示词 + 本局消息历史       │
└────────────────────────────────────────────────────────┘
```

职责边界（方案第八章）：**Agent 只能输出动作请求；位置、队列、票、通关、判负全部由模拟器结算。** 模型输出的文字只用于展示，不改变任何状态。

## 5. 模拟器

### 5.1 时间与确定性

- 固定步长 `dt = 0.1s` 世界时间；渲染按倍速（1x/2x/4x）推进若干步。
- 所有随机量来自带种子的 PRNG（mulberry32），同种子同指导 ⇒ 同一世界演化（模型输出本身除外）。MVP 默认固定种子 `1`，UI 可改种子用于对照。
- 世界只在 `engine.step()` 中推进；**决策等待期间不调用 step**，即“子弹时间”：玩家、NPC、事件计时、倒计时全部冻结。

### 5.2 场景布局（MVP 取值，单位米，60 × 30）

```
 x=0        14           26        36        44    60
  ┌─────────┬────────────┬─────────┬─────────┬─────┐
  │         │ TVM-1 y=6  │S1 y=6   │   ▓柱   │G1 y=5
  │ 入口    │ TVM-2 y=12 │S2 y=15  │         │G2 y=10 …
  │ (2,15)  │ TVM-3 y=24 │S3 y=24  │   ▓柱   │G5 y=25
  └─────────┴────────────┴─────────┴─────────┴─────┘
   售票厅                  安检墙     安检后大厅  闸机线  站台
```

- **售票机** TVM-1/2/3：位于 x=14，队伍向左（-x）排。
- **安检墙** x=26，只在三条安检通道处开口；S1/S2/S3 的安检机在墙口，队伍向左排，安检完成后被送到墙右侧出口点。
- **柱子** 两根（36,9）和（36,21），2m×2m，阻挡视线。
- **闸机线** x=44，五台闸机 G1–G5（y=5,10,15,20,25），队伍向左排；闸机之间是栏杆（阻挡通行，不阻挡视线）。
- **成功判定**：角色经闸机（或翻越）进入 x>44.5 的站台区域。
- 寻路：预置导航图（节点 + 边），`move_to` 在图上做 Dijkstra，沿折线行走，不穿墙。MVP 不做角色间碰撞（点可以重叠），只用队列位次表达拥挤。

### 5.3 角色

| 类型 | 步速 m/s | 售票 s | 安检 s | 过闸 s | 可观察特征 |
|---|---|---|---|---|---|
| 普通 normal | 1.3 | 6–9 | 5–8 | 1.5–2.5 | 无 |
| 老人 elderly | 0.8 | 10–16 | 8–12 | 3–5 | “行动缓慢的老人” |
| 带行李 luggage | 1.1 | 7–10 | 14–20 | 3–4 | “携带大件行李” |
| 赶时间 hurried | 1.7 | 4–6 | 4–6 | 1–1.5 | “步伐很快” |
| 玩家 player | 1.4 | 6–9 | 5–8 | 1.5–2.5 | — |

- 实际耗时在区间内由种子 PRNG 抽取；**Agent 只能看到区间，看不到抽样值**（方案第六章）。
- 通道倍率：S1 ×0.8（快），S2 ×1.0，S3 ×1.4（慢）；TVM 与闸机倍率 1.0。倍率作为公开信息（“通道效率”）在观察范围内提供。
- NPC：按剧本在 0–90s 内从入口生成约 32 人；约 65% 自带交通卡跳过售票。NPC 选择“眼前人数最少”的队伍（简单程序逻辑）。部分 NPC 带 `irritable` 特征（被插队会抱怨）。

### 5.4 队列与设施

- 队列 = 设施前的有序位次，位次间距 0.8m。加入队列：走到当前队尾位置后插入队尾；同一步到达者按实体 id 排序。
- 排到队首且设施空闲 ⇒ **自动开始办理**（MVP 决定：买票、安检、刷卡均为“排到即办理”，减少无意义决策；方案中“买票、安检、刷卡”对应三类设施的自动服务）。
- 离队：失去位次，可去别的队；办理中不可离队。
- 设施状态：`open` / `closed`（临时停用）/ `broken`（故障）。停用时队伍里的人被告知并需要自行改道；NPC 自动改道，玩家收到事件后自行决定。
- 闸机校验：无有效票则拒绝（“无有效票”），角色留在闸机前。

### 5.5 预设事件（固定情景，MVP 取值）

| 时间 | 事件 | 玩家如何得知 |
|---|---|---|
| 开局起 | G3 故障，不放行 | 进入观察范围看到“故障”标识 |
| t=25s | TVM-1 故障停用 | 在其观察范围内看到；若正在其队伍中直接收到通知 |
| t=40s | S1 临时停用，队伍需改道 | 同上，另有安检区广播（覆盖安检墙两侧 12m） |
| t=55s | S2 中一名乘客复检，额外 +10–15s | 观察范围内可见“复检中” |

### 5.6 违规、保安与判负

- 保安两名：A 守在安检出口（30,15）面向 +x；B 在闸机内侧沿 x=41 于 y=4–26 往返巡逻，朝向为移动方向。
- 视野：半径 12m，视角 110°，视线被墙和柱子遮挡（线段与矩形求交）；闸机栏杆不挡视线。
- **违规被保安看见 ⇒ 立即判负**（方案 1.1 补充规则）。违规持续期间（动作执行中）每一步都做发现判定；违规完成且不在视线内则不会事后判负，但会记入复盘。
- 乘客反应：被插队的 `irritable` 乘客会大声抱怨，抱怨声 10m 内的保安会转头看向该处 3 秒；这 3 秒内插队者若在其视线中，同样判定为被发现。
- 违规分级字段 `severity` 预留，MVP 所有违规被发现均判负。

### 5.7 结束条件与评分

- 限时 `180s` 世界时间（MVP 取值）。
- 成功：进入站台区；**成绩 = 过闸时刻的世界时间**（越短越好，不含思考暂停）。
- 失败：超时；违规被发现；连续 3 次决策失败（模型不可用）。失败无成绩。

## 6. 观察与信息限制

- 角色视野半径 12m、360°，视线受墙和柱子遮挡。
- **固定知识**（开局即知，写入 system 提示词）：地图、设施位置与编号、导航节点名、公开规则、各类乘客耗时区间、限时。
- **实时观察**（每次决策时提供，只含可见部分）：
  - 自身：位置、所在节点、当前动作、是否有票、是否已安检、所在队列与位次、剩余时间；
  - 可见设施：状态、队列人数、队中可见乘客特征、通道效率、是否有人在办理/复检；
  - 可见保安：位置与大致朝向；
  - 本次触发事件（到达、办理完成、动作失败、设施状态变化、广播、抱怨等）。
- 不提供：视野外的队列和状态、未来事件、实际抽样耗时。
- 局内记忆：服务端会话保存本局全部消息，旧观察带时间戳，模型能区分“上次所见”和“当前所见”。

## 7. Agent 运行层

### 7.1 动作工具（模型可调用）

| 工具 | 参数 | 说明 |
|---|---|---|
| `move_to` | `target`（导航节点名） | 走到某个位置 |
| `join_queue` | `facility`（如 `TVM-2`、`S1`、`G4`） | 走到该设施队尾并加入；排到即办理 |
| `leave_queue` | — | 离开当前队列 |
| `wait` | `seconds`（1–20） | 原地等待，结束后重新决策 |
| `attempt_creative` | `intent`（自然语言） | 常规流程外的尝试，由环境归类并按规则结算 |

每个工具都带必填 `reason` 字段（≤40 字），用作玩家可见的简短决策说明（方案第三章第四步），不额外调用模型。

工具定义使用 `strict: true`；模拟器在执行前再次校验参数与条件（目标存在、设施开放、是否已有票等），不满足则返回失败原因。

### 7.2 决策触发（事件驱动）

到达目的地；加入队列；办理完成/被拒；动作失败；`wait` 结束；可见设施状态变化（首次看到故障、停用）；广播；与自身有关的异常（被抱怨、所在队伍停用）；**排队中 20s 无事件的定期检查**（MVP 取值，避免完全无感知地干等）。同一步产生的多个事件合并为一次决策。

### 7.3 子弹时间与决策预算

- 触发决策 ⇒ GameRunner 停止调用 `step()`，界面显示“思考中”；收到有效动作后恢复。
- 新决策返回后：若是新动作则替换当前动作；若模型认为维持现状，可调用 `wait` 或 `join_queue` 当前队伍（视为保持）。
- **单次决策 ≤ 1024 token（方案 1.1）**：请求参数 `max_tokens: 1024`。在 Opus 5.5 上思考不能关闭、也不接受 `budget_tokens`，`max_tokens` 是唯一的硬上限，它覆盖“思考 + 说明 + 工具调用”的全部输出，因此思考链必然 ≤ 1024 token。同时设置 `output_config.effort: "low"` 让模型倾向简短思考。
- 若 `stop_reason == "max_tokens"` 且未产生工具调用，算一次决策失败。
- 决策失败处理：同一触发重试 1 次（追加“请直接调用一个工具”的提示）；仍失败则执行保底动作 `wait 2s` 并记入复盘；连续 3 次失败 ⇒ 本局终止（模型不可用）。
- 单局决策上限 60 次（MVP 取值）。用尽后不再调用模型，当前动作继续执行到底，空闲则原地等待（复盘中注明）。

### 7.4 模型调用细节（服务端）

```ts
client.beta.messages.create({
  model: AGENT_MODEL,                    // 默认 claude-opus-5-5
  max_tokens: 1024,                      // 单次决策硬上限
  thinking: { type: "adaptive", display: "summarized" },
  output_config: { effort: "low" },
  system: [...固定规则与地图, ...整理后的玩家指导],   // 带 cache_control，跨决策复用缓存
  tools, tool_choice: { type: "auto" },  // Opus 5.5 不支持强制 tool_choice
  messages: 本局历史（只追加，思考块原样回传）,
  betas: ["server-side-fallback-2026-07-01"], fallbacks: "default",
});
```

- 消息历史只追加不改写（思考块需原样回传）。每次决策的输入为上一工具调用的 `tool_result`，内容是“动作结果 + 新观察 + 触发事件”。
- `fallbacks: "default"`：模型因安全分类拒答时由服务端自动改由其他模型继续，避免对局卡死。实际服务的模型记入决策日志；做模型对比时可通过 `AGENT_FALLBACK=off` 关闭。
- 思考摘要（`display: "summarized"`）只展示给玩家，不作为状态依据。
- 记录每次 `usage`（输入/输出/缓存 token）与真实耗时，进入复盘。

### 7.5 赛前指导整理

- 玩家输入 ≤ 300 字（按 Unicode 字符计，前后端都校验）。
- 服务端一次调用，输出结构化结果：`{ summary, priorities, risk, rules, creativeIdeas, initialPlan }`（使用 `output_config.format` 结构化输出）。
- 要求：保留原意，不添加玩家没表达的偏好，不赋予任何能力；与系统规则冲突的内容标注“不可执行”并说明。
- **整理结果在开局前展示给玩家**，玩家可确认开局或返回修改。
- 权限由环境强制：指导中写“你知道所有队伍长度”“你已经有票”不会产生任何效果，因为观察和状态只由模拟器提供。

### 7.6 离线规则 Agent

`HeuristicAgent` 在浏览器内运行，不调用模型，实现“默认守序通行”：去最近的开放售票机 → 估算各可见安检队伍耗时选最短 → 选闸机。用途：

1. 无 API Key 时也能演示和调试完整流程（界面明确标注“离线规则 Agent，非大模型”）；
2. 自动化测试：验证“默认流程在固定情景下能通关”。

## 8. 创造性行动

- 入口：`attempt_creative(intent)`。
- 归类：服务端用模型把意图映射到**封闭机制清单**中的一项或 `unsupported`（结构化输出，枚举约束），保证相近表达得到一致归类；离线时用关键词规则。
- 结算：完全由模拟器按规则执行，模型不决定结果。

| 机制 id | 含义 | 条件 | 执行 | 违规 |
|---|---|---|---|---|
| `cut_in_line` | 插队到某队前部 | 角色位于该队附近（≤3m） | 1.5s 插到第 2 位（不抢正在办理者） | 是 |
| `jump_gate` | 翻越闸机/栏杆 | 角色位于闸机线前 ≤1.5m | 2.5s 越过闸机线，到达站台即成功 | 是（逃票） |
| `unsupported` | 其他 | — | 不执行，返回“不支持”与原因 | — |

- MVP 机制范围遵循方案 1.1 “以目前讨论的基础能力为范围，不额外扩展新机制”；清单是数据表，后续可增补。
- 不在界面中列出清单（方案第七章）；失败反馈说明具体限制（如“离闸机太远”）。

## 9. 记录与复盘

- `EventLog` 记录每步关键事件；`DecisionRecord` 记录每次决策的触发、观察摘要、思考摘要、动作、理由、结果、token 用量、真实耗时、实际服务模型。
- 结束报告：
  - 结果与成绩（过闸用时）/ 失败原因；
  - 时间分解：行走、排队、办理、等待；
  - 路线轨迹（叠加在地图上）；
  - 关键决策列表（当时观察 → 动作 → 实际结果）；
  - 异常事件与违规记录；
  - 决策次数、token 用量、思考暂停总时长（现实时间，不计入成绩）。
- 报告可导出 JSON。同一种子 + 修改后的指导即可做对照重试。
- 局结束调用 `DELETE /api/session/:id` 清空服务端局内记忆。

## 10. 接口定义（摘要）

```
POST /api/guidance/normalize  { text }                     → { guidance, plan }
POST /api/session             { guidance, scenarioBrief }   → { sessionId }
POST /api/agent/decide        { sessionId, turn }           → { action, reason, thinking, usage, model, latencyMs, error? }
POST /api/creative/classify   { intent, context }           → { mechanic, reason }
DELETE /api/session/:id                                     → 204
GET  /api/health                                            → { llm: boolean, model }
```

`turn` 为上一动作结果 + 新观察 + 触发事件（结构化 JSON，服务端渲染为文本）。

## 11. 测试策略

- 单元：PRNG 确定性、视线遮挡、队列位次与离队、设施停用、闸机验票、违规发现、计时与评分。
- 集成：离线 Agent 在默认种子下限时内通关；同种子两次运行结果完全一致；保安视线内翻闸判负、视线外翻闸成功。
- 服务端：工具参数校验、300 字限制、无 Key 时 `/api/health` 返回 `llm:false`。
- 真实模型调用不进自动化测试（花费真实额度），用手动冒烟测试验证。

## 13. 风险与待定

| 风险 | 应对 |
|---|---|

## 14. 实现核对与约束（本轮交付）

本节优先于上文的开发前设计草案；未将实现初值冒充用户已确认规则。

### 实际文件与接口

- 队列、设施、移动合并在 `src/sim/world.ts`，没有单独的 queues.ts。
- `src/agent/runner.ts` 负责暂停、预算、重试和报告；没有额外的报告模型调用。
- 模型层为 `server/claude.ts`（局内决策）与 `server/structured.ts`（赛前整理/意图归类）；模型参数配置在前者。
- 会话创建接口是 `POST /api/session { guidance, normalized }`；不接受客户端自定义世界规则作为 system 提示词。
- 创造性归类接口是 `POST /api/creative/classify { intent, observation }`。
- 导航图按节点可直达关系构造可见性边，使用 Dijkstra；程序只选几何路径，不选择策略目的地。

### 规则的实际取值

- 两根 2×2 米柱子的左上角是 (35,11)、(35,17)，以 layout.ts 为准。
- 开局有 21 位已排队乘客，另有种子生成的 2–5 秒间隔客流，持续到 90 秒；并非固定总计 32 人。
- NPC 按“预计排队耗时 + 路程”选设施，不调用模型。NPC 使用程序全局信息，玩家 Agent 仍只拿局部观察；未来公平竞技需要另做规则。
- 设施临时停用时，正在办理的人完成当前服务，等待者离队；“故障”暂采用同样语义，没有中断服务的复杂恢复逻辑。
- 复检事件在 55 秒时给 S2 的下一名非玩家服务附加 10–15 秒，不保证 55 秒整就开始复检。
- 玩家观察逐个过滤乘客的距离与遮挡。设施的 queueLength 表示可见排队人数，不保证包含被遮挡者；自身队内位次是排队状态反馈。
- 插队/翻闸是本轮选择的两种有限机制，未扩大为无限能力；具体数值仍需体验测试。翻闸距离阈值为 1.7 米。
- `wait` 保持行走/排队/服务不中断；离队会立即触发下一次决策。非法跨区域移动先拒绝，不丢失已有队列位次。

### 模型预算与错误处理

- `max_tokens <= 1024` 限制每次角色决策请求的全部输出，不只是可见说明；这比单独限制思考更严格，可能更容易截断。
- 同一决策机会允许一次重试，两次请求分别受 1024 限制；累计用量包含二者。每局上限 60 个决策机会，最多 120 次角色决策请求（SDK 自动重试已关闭）。
- 三次连续决策失败终止本局，无成绩，但这属于技术失败，不等同于角色违规死亡。
- API SDK 超时 20 秒，浏览器请求超时 30 秒。终止对局立即结束前端对局并清理会话，迟到动作不执行；已经发给供应商的请求未必立即取消或免于计费。
- 赛前整理允许 4096 输出 token；环境意图归类独立请求允许 1024。报告的 token 累计只覆盖局内角色决策，不包含这两类辅助调用，也不提供金额账单。
- 拒答回退默认开启，实际模型记录在日志里。做严格模型比较应关闭回退；服务端回退内部的用量以供应商 usage/账单为准。
- 复盘仅显示模型返回的简短说明或摘要，不要求输出私有的完整思考链。

### 交付限制

- 玩家上帝视角与角色受限观察分离；地图圆/扇形为范围示意，未按墙体裁剪。实际发现与观察使用遮挡判定。
- 报告支持 JSON 导出、轨迹和同种子再运行，但不是存档式逐帧回放；刷新页面会丢失未导出的报告。
- 种子固定初始条件和随机序列；不同动作会影响队伍及事件消费顺序，不保证所有后续状态完全一样。
- 本地可信客户端执行模拟；Express 监听 127.0.0.1。未实现账号、鉴权、计费限流、竞技防作弊或公网部署加固，不应直接开放到公网。
- 真实模型整局未测试，因此默认模型能否在 1024 token 下稳定给出有效动作、不同自然语言指导的行为差异与实际费用仍待真实接口验收。
