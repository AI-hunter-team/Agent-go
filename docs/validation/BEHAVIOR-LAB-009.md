## 原因与调整

- 2026-11-01用户截图原文：“想办法引开保安注意翻越栏杆。不买票。直接抢有票乘客的票”。旧日志中两次上游均200/completed，第一次对应条目检查失败，第二次 validPlan 失败；旧失败日志没有方案正文，无法断言第二次具体哪项不合格。
- 原实现把初始策略提案与旧 normalized 摘要容量绑在一起：最多8项、每字段1000字符、摘要总8000字符；coverage 缺项或错误也会阻断准备。这些是实现门槛，不是用户需填写字段的产品要求，也不能证明实际动作是否合法。
- 现在初始方案不再按8项或单段1000字符拒绝；支持普通段落、字符串/对象步骤列表、常见字段别名及部分缺字段。对象步骤的条件/补充参数完整保留，不能仅提取 instruction 而丢掉条件。用户原文仍按来源逐项保存。
- 默认规划原则仅补充未写部分：目标、公开地图、必要观察、准备、变化应对；明确原指导优先，不追加相反的购票/守序路线。无法读取模型返回或调用失败时形成明确标注的“基础准备稿”，不能冒充真实模型生成成功。
- 对应说明按每项处理：有效项保留，缺失/重复/错误引用标“尚未核对”，不再整份失败；正向游戏动作误标为禁止时撤销该判断并提示。对应检查不等于通用语义证明。
- 原 normalized 接口仍按原边界验证客户端输入；对长初始方案只产生明确的兼容摘要，完整方案单独绑定到服务端 Session.journeyPlan，再完整放入角色输入和复盘元数据，不靠截断来通过旧容量。第三方客户端不能提交伪造完整方案覆盖已准备结果。
- 新诊断记录仅包含可展示的模型 output_text、读取失败原因、默认/适配来源与补充说明；不读隐藏推理，沿用密钥脱敏。解析失败也保留已计费用量。不自动重试；旧三调用诊断若只得到基础稿会停止后续付费调用。

## 保留的边界

- 这次修改针对方案输出/适配，不扩大现有300字自然语言指导输入容量，也不要求用户输入JSON或固定字段。
- 实际动作仍有独立规则，包括单次执行计划步数、可见目标/距离、真实持物、碰撞、保安视线、时限和反抗。初始方案写9项不代表一次工具调用可无条件执行9项。
- 没有承诺网络/凭据/供应商故障时仍有真实模型生成，也不把基础稿当成已经理解全部意图或保证动作成功。服务未启动或模型未配置仍需恢复运行条件。
