# 开发、文档与协作流程

状态：现行仓库协作约定。产品与实现的来源按 [文档导航](README.md) 查找；本文件不增加玩法范围。开发 Agent 指辅助开发的工具，角色 Agent 指游戏内的行动主体。

## 1. 开始任务

1. 阅读 [AGENTS.md](../AGENTS.md)、导航、[路线图](ROADMAP.md) 和 [中央工作记录](开发计划.md)，再读任务涉及的产品、设计、源码及历史验证。检查是否还有更深层目录规则。
2. 在仓库根目录运行下列只读命令，记录实际基线、worktree 和已有修改。保留无关改动；不运行破坏性清理，不覆盖别人的文件。

   ```sh
   git status --short --branch
   git worktree list
   git rev-parse HEAD
   git log -5 --oneline
   ```

3. 从[简报模板](templates/task-brief.md)创建 `docs/tasks/<任务编号>.md`，填写单一负责人、目标/交付物、基线分支与完整 commit、允许/排除路径、依赖、接口、验证、完成条件、集成负责人及交接方式。Agent 执行者可以署明实际工具/会话，不能虚构人类负责人。未落实负责人或必要接口时不启动相关并行工作。
4. 单任务且当前工作区空闲时可在此建立 `codex/<任务短名>` 分支；团队已有分支约定时沿用。当前目录承载其他任务或同机并行时，必须独立 worktree，不能只换分支继续共享目录。

   ```sh
   git switch -c codex/<任务短名>
   ```

   或在已核实的本地基线创建独立工作区（占位符需替换）：

   ```sh
   git worktree add -b codex/<任务短名> ../<仓库名>-<任务短名> <基线commit>
   ```

   创建分支或 worktree 不代表已经拉取远端。使用本地 `origin/main` 时说明其为本地引用；需要远端新状态时再按任务授权同步并核实。

## 2. 目录职责与依赖

| 路径 | 职责与改动时要核对的消费者 |
|---|---|
| `src/shared/` | 前后端共用的动作、观察、指导与报告类型；检查 `sim`、`agent`、`ui`、`server` 和测试 |
| `src/sim/` | 世界、规则、几何/导航、观察、NPC、结算；检查运行器、离线 Agent、UI 与规则测试 |
| `src/agent/` | 角色 Agent 接口、离线/远程实现、运行器；检查模拟时间、会话生命周期、报告与 UI |
| `src/ui/` | React 面板、Canvas 渲染、日志与报告导出；不能用展示层绕过模拟规则 |
| `server/` | Express API、局内会话、提示词、工具与模型调用；检查远程客户端、共享类型及伪客户端测试 |
| `tests/` | Vitest 自动化与使用伪响应的模型接口测试；不是付费模型整局验收 |
| `design/`、`docs/` | 视觉历史、产品/技术说明、任务与验证证据；按导航区分现行和历史 |

实际依赖与脚本唯一来源是 [package.json](../package.json)，解析版本由 [package-lock.json](../package-lock.json) 固定。使用 npm，安装用 `npm ci`，不新增第二套锁文件。README 建议 Node.js 24 LTS；仓库没有 `engines` 或 Node 版本固定文件，报告需记录本机 `node --version`、`npm --version`，不将旧设计的 Node 20+ 写成已验证矩阵。

依赖变更需在允许范围内说明原因，同步 manifest 与 npm 锁文件，并验证可复现安装；本次文档任务不改依赖。根配置、共享类型、API/动作工具、导出格式及共用测试数据变动由集成负责人协调消费者与修改顺序。

## 3. 多人和多开发 Agent 协作

- 每个并行任务一个负责人、独立分支和独立工作区。同一阶段每个文件只归一项任务；不同分支也不允许各自重写共享文件。简报用路径清单分配归属，重叠先排顺序或交给集成任务。
- 集成负责人在 [中央工作记录](开发计划.md) 登记任务、归属、依赖与顺序；并行期间只有集成负责人修改中央记录和路线图。各任务在自己的简报、验证报告和 PR 中提交状态/交接，由集成人汇总。
- 共享接口先在现行设计的相应章节或任务变更记录中明确字段、错误/超时语义、兼容性、测试样例和消费者，再启动依赖它的任务。占位实现需标为临时并写明替换条件，不能让多个任务分别定义同一接口。
- Agent 只改已分配路径。需要扩大范围时先写明影响、调整文件归属；普通实现选择在已授权范围内自行处理，产品决策、权限或实质规则冲突才向任务发起者确认。
- 单个历史任务的串行要求只约束该任务，不构成全项目永久禁并行。工具专属规则只在实际使用时添加短入口并引用共同规范；已有 [CLAUDE.md](../CLAUDE.md) 不复制另一套流程。
- 任务暂停或换人/换 Agent 时，先写当前分支与 commit/未提交状态、已做/未做、命令结果、证据、阻塞和下一步。聊天可以辅助沟通，仓库及 PR 才承载可接续信息。

## 4. 文档与接口变更

- 每份文档标清身份：草案/待确认、现行基线、实现核对、验证快照或历史。已批准规范附可核实的批准依据；没有依据就写待确认，不把提案改写成已实现功能。单一规则只在导航指定的来源维护正文。
- 规范与实现不一致时，在现有技术方案的差异章节或任务简报记录“预期、实际、影响、后续入口”，链接两端。不能靠改写规范掩盖缺陷，也不能通过协作任务改变产品范围。
- 变更已冻结或对外承诺的接口、数据格式、验收标准前，记录原因、消费者影响、兼容/迁移、验证及回退办法，附所需授权依据。尚未取得必要授权时只推进独立的调查与设计，不执行依赖该授权的变更；批准后同步规范、实现和测试。
- 当前内部接口沿用技术方案及源码，不另建重复协议。是否承诺对外兼容、版本策略和冻结由具体任务确认；不能把“尚无冻结记录”理解成可随意破坏兼容。
- 更新现行说明时保留必要历史证据。过时材料优先加历史标记和现行入口；迁移/归档后更新导航、入链和相对路径，保留原结论的版本与限制。
- 不保存密钥、生产凭据、个人机器绝对路径或原始大型日志/截图/报告。用仓库相对路径或稳定的证据编号；大型产物只存脱敏摘要和可访问的证据索引。缺失的历史附件明确标注，不制造下载链接。

## 5. 开发与分层验证

以下 npm 命令均来自 `package.json`。先执行 `npm ci` 安装锁定依赖，已有可用安装时无需每次重装。开发启动命令会常驻：

| 用途 | 真实命令 | 说明 |
|---|---|---|
| 同时启动前后端 | `npm run dev` | Vite 默认 5173，代理 `/api` 到本机 Express 默认 8787；端口逻辑见 [vite.config.ts](../vite.config.ts) 与 [server/index.ts](../server/index.ts) |
| 分开启动 | `npm run dev:web`、`npm run dev:api` | 后者带 watch；`npm run start:api` 单独启动 API，不带 watch |
| 类型检查 | `npm run typecheck` | `tsc --noEmit`，覆盖范围见 [tsconfig.json](../tsconfig.json) |
| 自动化测试 | `npm test` | `vitest run`，测试发现与 Node 环境由 Vite 配置定义 |
| 静态前端构建 | `npm run build` | `tsc --noEmit && vite build`；不打包部署 Express API |
| diff 格式 | `git diff --check` | 检查已跟踪文件的 diff；新文件还需在暂存后检查或单独检查 |

按改动风险执行，不写镜像实现式测试：

1. **日常快速检查**：代码改动运行类型检查及相关测试。可用 Vitest 已有文件过滤方式，例如 `npm test -- tests/server.test.ts`；在简报中填写真实受影响的文件。共享模块变化还需检查消费者与边界测试。
2. **代码提交前完整检查**：`npm run typecheck`、`npm test`、`npm run build`、`git diff --check`。UI 交互/布局变化按风险增加浏览器检查，不以报告渲染单测代替真实操作。暂存后再跑 `git diff --cached --check`。
3. **纯文档检查**：检查相对链接及锚点、命令来源、导航/权威来源/术语一致性、历史与当前状态、敏感内容及完整 diff；执行 `git diff --check`，新文件也检查行尾空白。无业务或配置变化时可说明理由跳过 npm 检查，不强制安装依赖。
4. **集成及实际验收**：浏览器启动方式见 README；按产品方案的验收目标覆盖完整用户路径和本次影响。真实模型需要已授权的可用凭据/额度，记录模型配置、种子、指导条件、结果、费用/延迟证据及限制；不入库凭据。`/api/health` 仅说明配置存在，不证明认证、模型可用或整局通过。离线规则 Agent 不理解自然语言，不能证明指导差异。相同种子也不保证不同动作后的世界演化完全相同。

每次验证使用[报告模板](templates/validation-report.md)写入 [validation](validation/README.md)，逐项记通过/失败/未运行/跳过/阻塞、原因、版本、脏工作区状态、实际命令与证据。修复后复验受影响项；集成后验证合并后的版本。构建或 CI 成功不能替代浏览器、真实模型或其他实际验收。

当前缺口：仓库没有 lint、格式化、Markdown 链接检查、浏览器自动验收或统一 `check` 脚本，也没有已跟踪的 CI 工作流。文档可使用一次性本地链接审计，但需记录其方法，不能声称仓库已有相应 npm 命令。是否新增工具和 CI 另开任务；本次不改配置或工作流。

## 6. 提交、审查、集成与交接

- 提交围绕一个目标，可审阅、可构建、可回退；沿用日志中的 Conventional Commits 风格，如 `docs:`、`fix(sim):`、`feat(agent):`、`test:`。提交前审阅 `git diff`、新文件和暂存内容，避免混入无关改动。提交、推送只在当前任务授权范围内执行。
- 使用 [PR 模板](../.github/pull_request_template.md)链接简报和验证报告，写清任务负责人/集成人、允许范围、前置任务、接口变化、未验证项、风险、回退及接手步骤。无 PR 的本地任务也把同样信息留在简报中。
- AI 审查产生待核实意见，开发者负责核对事实、风险和测试；没有真实人工审查就写“人工审查未进行”，不能替人批准。
- 集成负责人按接口依赖顺序核对基线、消费者与文件归属，处理冲突，在集成版本上执行适用检查，再集中更新中央记录。远端合并、发布、部署、生产数据修改和真实设备操作必须有当前任务明确授权；不新增重复确认流程，也不把普通本地检查当作外部操作。
- 分别记录四项状态：**实现完成**（含文档交付）、**软件检查通过**、**实际验收通过**、**已合入**。每项附范围与证据，允许“不适用/未运行/阻塞”；前三项不自动推出已合入。集成前有新改动则复核报告仍适用。
- 团队检查要求与平台门禁分开写。本次仅核实本地仓库，远端分支保护、必需检查及自动合并规则未核实，不声称已经生效。长期维护人与平台策略由团队另行决定。
